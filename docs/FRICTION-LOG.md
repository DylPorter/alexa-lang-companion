# Friction Log — Sala (Alexa+ track)

Per the hackathon rules, friction log entries are **optional and can earn up to a 10% judging
bonus**, assessed by Amazon's internal review during the Stage 1 downselect. Each entry below is
written in the required shape: the specific task attempted, the steps taken, expected vs actual,
severity, the workaround used, and an actionable suggestion.

These are entries from the 15–22 Oct 2026 build window for this project only. The Fire TV track's
entries live in the parent project note and are not part of this submission.

Cloud account identifiers are redacted; they add nothing to a tooling report and this repo is
public.

## 2026-10-20 — Sala A1 (Alexa+ MCP server)

- 2026-10-20 — **MCP SDK lags the MCP spec revision**: task: target MCP spec 2026-07-28 via the official TypeScript SDK (SPEC.md requirement "current 2026-07-28 via the official SDK"). Steps: `npm view @modelcontextprotocol/sdk` → latest **1.32.1**; read `dist/esm/types.js`. Expected: SDK implements the current spec revision. Actual: `LATEST_PROTOCOL_VERSION = '2025-11-25'` — the newest published SDK implements the PREVIOUS revision; 2026-07-28 is not reachable through the official SDK today. Severity: **minor** (hackathon requires ≥ 2025-11-25, which the SDK does implement, and Streamable HTTP is fully there — HTTP+SSE correctly deprecated). Workaround: pin SDK 1.32.1, negotiate 2025-11-25, record the gap honestly in README. Suggestion: SDK release notes should state the implemented spec revision on the npm landing page; hackathon docs should say which revision the official SDK actually ships.
- 2026-10-20 — **Claude Code env exports `ANTHROPIC_API_KEY` as an empty string**: task: ProxyLLM live smoke via the qwen proxy. Steps: standard `??` fallback chain `ANTHROPIC_API_KEY ?? ANTHROPIC_AUTH_TOKEN`. Expected: fall through to the real token. Actual: `ANTHROPIC_API_KEY` is *present but empty* (`len=0`) in both shell env and `~/.claude/settings.json`, so `??` picks `""` and the client throws "requires ANTHROPIC_API_KEY" while a valid `ANTHROPIC_AUTH_TOKEN` (len 114) sits right beside it. Severity: **minor** (cost one debug cycle; would trap every Anthropic-compatible client using nullish fallbacks). Workaround: select first NON-EMPTY candidate. Suggestion: don't export empty-valued keys in `settings.json` env injection, or document that `ANTHROPIC_API_KEY=""` is a deliberate "use AUTH_TOKEN" signal.
- 2026-10-20 — **qwen proxy transiently returns empty chat content**: task: two-turn live smoke chat. Expected: both turns reply. Actual: turn 1 replied normally; turn 2 returned HTTP 200 with **empty content** (once, not reproducible on immediate re-run). Severity: **minor** (flake). Workaround: retry-once on empty reply + honest fallback line in the chat tool. Suggestion: proxy should surface an error instead of a 200-with-empty-content.
- 2026-10-20 — **SQLite FTS5 `MATCH` rejects table aliases**: task: JOIN an external-content FTS5 table with its base table. Steps: `FROM activities_fts f JOIN activities a ON a.id=f.rowid WHERE f MATCH ?`. Expected: alias works like any table. Actual: `SqliteError: no such column: f` — the left side of MATCH must be the literal FTS table name, not its alias; the error message points nowhere near the real problem. Severity: **minor**. Workaround: use the unaliased table name in MATCH and the qualified `table.rank` for bm25 ordering. Suggestion: SQLite docs/error text should name the constraint ("MATCH lhs must be the FTS table name").
- 2026-10-20 — **FTS5 `unicode61 remove_diacritics 2` does not fold ligatures**: task: accent-insensitive recall for French learner text. Expected: "soeur" matches "sœur" the way "cinema" matches "cinéma". Actual: é→e folds fine, but œ is a LIGATURE, not a diacritic — it survives folding and "soeur" ≠ "sœur". Severity: **minor** for a French-learning product (common words: sœur, œuf, cœur, œuvre). Workaround: documented limitation + tests asserting the real behaviour; a production fix would index a ligature-expanded shadow copy. Suggestion: an FTS5 tokenizer option for ligature expansion (œ→oe, æ→ae, ß→ss).
- 2026-10-20 — **`unshare -rn` offline proof needs `lo` brought up manually**: task: prove `npm test` is truly zero-network by running it in a network namespace. Expected: loopback-only tests pass. Actual: fresh netns has loopback DOWN, so the localhost MCP integration test fails with connection errors that *look* like a network dependency. Severity: **nit**. Workaround: `unshare -rn sh -c 'ip link set lo up; npm test'` → 56/56 green with no external interfaces. Suggestion: none (environment note for future offline-proof runs).
- 2026-10-20 — **dotenv 17 prints a promo banner on every load**: task: silent `.env` loading in the server + smoke script. Actual: dotenv ≥17 writes an "[dotenv@17.x] injecting env" banner to stderr on load, which pollutes test/smoke output. Severity: **nit**. Workaround: `dotenv.config({ quiet: true })`. Suggestion: banners off by default for library use.

## 2026-10-20 — Sala A2 (web sim)

Steps: read `webStandardStreamableHttp.js` in SDK 1.32.1. Expected: `allowedOrigins: []` + `enableDnsRebindingProtection` rejects every Origin. Actual: validation runs only `if (this._allowedOrigins.length > 0)` — with an empty list ANY origin passes the SDK check; the real browser blocking in A1 came from the refused OPTIONS preflight (405) plus the absence of ACAO headers, neither of which the SDK owns. ## 2026-10-21 — Sala Bedrock enablement (AWS Builder path)

- 2026-10-21 — **Bedrock short-term API key returns an "invalid key" 403 with no hint that it died with the console session**: task: first live Bedrock smoke for the Sala MCP server (`npm run smoke`, `amazon.nova-lite-v1:0`, us-east-1). Steps: console → API keys → Generate short-term API keys, paste into the gitignored `.env`, run the smoke ~40 minutes later having re-authenticated to the account in between. Expected: a working call, or an error naming the actual problem. Actual: `AccessDeniedException` with `Authentication failed: Please make sure your API Key is valid.` in all eight regions probed (us-east-1/2, us-west-2, ca-central-1, eu-west-1, eu-central-1, ap-southeast-1/2), and identically for a deliberately bogus model id, while a request with no header at all returned `Authorization header is missing` — which placed the failure in the authentication layer, not model access. The key string was well-formed (`bedrock-api-key-` prefix, 3359 chars, no whitespace, no truncation, no CR), so the only real cause was documented on a different page: "The key expires when your console session expires (max 12 hours)." Severity: **major** — ~20 minutes of region/parse/clock bisection. Workaround: re-mint and use it within the same console session, or move to SigV4. Suggestion: the runtime error should say "expired or console session ended" (or return the key's `valid until` in the response), and the console should print an expiry timestamp next to the generated key.
- 2026-10-21 — **Bedrock API keys are silently unavailable on an AWS Organization member account; the api-keys doc never mentions SCPs**: task: same smoke, second key, generated as long-term so it would survive session changes. Steps: console → API keys → long-term → paste → smoke. Expected: success, or a normal IAM authorization error. Actual: `User: arn:aws:iam::<ACCOUNT_ID>:user/<GENERATED_KEY_USER> is not authorized to perform: bedrock:CallWithBearerToken on resource: * with an explicit deny in a service control policy: arn:aws:organizations::<MANAGEMENT_ACCOUNT_ID>:policy/<ORG_ID>/service_control_policy/<POLICY_ID>`. The account created for this hackathon turned out to be an Organizations **member**, and the org denies the bearer-token action outright, so the entire API-key mechanism is unusable regardless of key type or expiry. `api-keys.html` contains no mention of Organizations, SCPs, or `bedrock:CallWithBearerToken`, and calls this auth method "Recommended for production use". Severity: **major** — a documented and recommended path is unavailable for a large class of accounts, discoverable only by running it. Workaround: SigV4 with an IAM user plus an explicit `bedrock:InvokeModel` policy (the repo already supports both shapes). Suggestion: state the SCP caveat on the API-keys page and name `bedrock:CallWithBearerToken` in the key-creation dialog so account admins can pre-approve it. Credit where due: the error message itself was excellent — explicit deny, action, resource, and the exact SCP ARN, which is why this one was diagnosable in a single shot.

- 2026-10-21 — **Nova model ids and the `temperature: 0` floor are documented in different doc trees from Converse**: task: point the existing `ConverseCommand` code at a cheap non-Anthropic model. Steps: pick `amazon.nova-lite-v1:0`, keep the review phase's `temperature: 0`. Expected: one uniform request shape across providers, per the Converse API reference. Actual: the Nova request schema restricts temperature to **0.00001–1**, so a literal 0 (the obvious choice for deterministic JSON extraction) is invalid, and that constraint is not stated on the Converse page, which lists no per-model parameter ranges at all. Separately, model-id shape is per-provider and easy to get backwards: Claude and Llama need the `us.` geo-profile prefix because they have no In-Region endpoint, while Nova is In-Region so the **bare** id is correct and prefixing it would be wrong — and the Claude model card contradicts itself, printing "In-Region endpoint URL: N/A" in its own availability table while using the bare id in its own sample code. ## 2026-10-21 — our own tooling (disclosed for completeness, not a vendor finding)

- 2026-10-21 — **our `npm run smoke` exited 0 while the backend was completely dead**: task: use the smoke as AWS Builder acceptance evidence. Steps: run it against an invalid credential. Expected: non-zero exit plus the provider's error text. Actual: `chat#1: {}`, `extractionPath: undefined`, `review: undefined`, and **exit 0**, because an MCP tool failure is a *result* with `isError` set rather than a thrown exception, so the script's `catch` never ran and AWS's message was discarded. This is the same class of bug the friction log exists to catch, aimed at us: a silently-passing check would have let a proxy recording go out labelled Bedrock. Severity: **major for our own evidence quality**. Workaround: fixed in-repo (`e5139c1`) — a direct one-turn `preflight()` per backend before the MCP stack exists, `isError` surfaced with its text, any attempted-but-failed backend sets `process.exitCode = 1`, and the run prints which credential shape resolved (names only, never values). `GATED` with no creds stays non-fatal by design. Suggestion to the MCP SDK, same as the A1/A3 entries: give tool results an unambiguous machine-readable failure signal so a client cannot mistake `isError` for a successful empty call.
- 2026-10-22 — **our own launcher could half-boot into a convincing dead demo (found by running a clean clone as the teammate)**: task: prove Alan's cold run works from a fresh clone. Steps: `SALA_LLM=echo npm run demo` on a machine where port 3000 belonged to another process. Expected: it fails loudly. Actual: Vite came up and served HTTP 200 while the server died on `EADDRINUSE`, so the sim looked alive next to a dead backend, and the first `--kill-others-on-fail` attempt still didn't cover it because the killed server exited with code **0** and that flag only reacts to non-zero exits. Severity: **major for the teammate path** — exactly the night-before-video failure mode. Workaround: fixed in-repo (`1a706b1`) — `demo.sh` pre-flights both ports with `ss` and exits 1 with the override spelled out, and the launcher uses `--kill-others`. Measured: busy 3000 → real exit code 1, nothing booted; `PORT=3100 SIM_PORT=5199` → banner `LLM backend: echo`, `/health` `{"ok":true,"backend":"echo"}`, sim 200; killing only the server → both ports free inside 5 s. README troubleshooting documents both. Suggestion to ourselves, generalised: any one-command demo entry point should verify its own ports before starting anything, because a partial boot is worse than a crash.
